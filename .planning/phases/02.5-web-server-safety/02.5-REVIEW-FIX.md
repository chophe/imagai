### WR-01: `command` field is not type-checked — non-string JSON returns 500 + internal error text

**Files modified:** `src/imagai/web_server.py`, `tests/test_web_server.py`
**Commit:** `657d0d3`
**Applied fix:** Added `if not isinstance(command, str): return 400` between
`command = data["command"]` and `shlex.split(command)`, with the error body
`{"success": false, "error": "Command must be a string"}`. The review's
suggestion was applied verbatim: the presence check stays, the type check
precedes the parse. Previously `{"command": 123}` / `[...]` / `{...}` reached
`shlex.split`, which raises `AttributeError` (not `ValueError`), escaped the
inner `except ValueError`, and was answered by the outer `except Exception` as
a 500 carrying `"'list' object has no attribute 'read'"` to the caller.
`None` returned 400 only by accident of shlex's own `ValueError`; the contract
is now type-independent, including for `true`.

**Regression test:** `test_generate_cli_rejects_non_string_command` — posts
`123`, `["imagai","generate"]`, `{"a": 1}`, `None`, and `True`, asserting
`400`, `success is False`, the exact error string, and `m.called is False`
(no subprocess). Verified RED against the pre-fix source (`500 INTERNAL
SERVER ERROR` at the first payload) and GREEN after.

### WR-02: set-diff returns a concurrent request's file (SEC-08 residual, acknowledged)

**Files modified:** `src/imagai/web_server.py`, `tests/test_web_server.py`
**Commit:** `303f318`
**Applied fix:** Added `import threading` and `_GENERATE_CLI_LOCK =
threading.Lock()` next to `_png_snapshot()`, and wrapped the entire
`before = _png_snapshot()` → `subprocess.run(...)` → `sorted(_png_snapshot() -
before)` block in `with _GENERATE_CLI_LOCK:`. This is the upgrade path CONTEXT
D-04 named verbatim and the review recommended; the `ponytail:` comment at the
diff (which recorded the ceiling) is replaced by the real serialization, and
the replace-by-lock is documented in the new comment's own `ponytail:` note.

**Measured cost, as asked.** The lock is held across the subprocess call, so
concurrent `/api/generate-cli` requests now run strictly sequentially — a
second caller waits behind the first's subprocess, bounded by the existing
300s timeout. That is the whole endpoint's throughput ceiling, not a partial
one, and it is now asserted by the test rather than left to chance. For an
unauthenticated local dev-server endpoint whose only other consumer-facing
problem is unbounded argument cost (IN-04), serializing it also caps the
concurrent-spend surface at one in-flight generation — so the trade is
directionally right, not merely the smallest change. The alternative shape
(per-request output subdirectories) would remove the serialization but
requires the CLI save layer to honor an output root, which is not this phase's
file and not a safe drive-by edit.

**Not closed by this fix (see Observations):** `/api/generate` writes to the
same directory and does not take this lock.

**Regression test:**
`test_generate_cli_concurrent_requests_return_only_their_own_images` — starts
request A, waits (event, not sleep) until A is genuinely inside its mocked
subprocess, then starts request B; A's mock holds until B has written its file.
Assertions: both responses are 200; `A's generated_images ==
["from_request_A.png"]`; `B's == ["from_request_B.png"]`; both files exist on
disk (proving B's write really landed inside A's window); and the two run
spans do not overlap. Verified RED against the pre-fix source — A's response
contained `from_request_B.png`, the review's demonstrated defeat reproduced
exactly — and GREEN after.

## Skipped Issues

### IN-01: Overwrite-in-place returns an empty `generated_images` list

**File:** `src/imagai/web_server.py:325`
**Reason:** The correct behavior is ambiguous, and the obvious fix conflicts
with the SEC-08 contract this phase exists to enforce — reported rather than
guessed, as instructed.

The finding is real: a command that overwrites an existing filename
(`imagai generate -o old.png`, or a repeated deterministic auto name) leaves
the path inside `before`, so the set-diff excludes it and a successful request
answers `generated_images: []`. Making it visible requires detecting which
pre-existing files the run rewrote, i.e. comparing `stat()` (size, `mtime_ns`)
before and after. That is the mtime-window heuristic this phase deliberately
deleted (the old 300-second window), and it reintroduces the same
mis-attribution class under a different name: with no serialization on the
other write path, a foreign writer that overwrites a pre-existing name during
the run is indistinguishable from our own overwrite.

That window is not theoretical. Verified empirically during this fix (probe,
then deleted — no commit, no test left behind): with a mocked
`generate_image_core` writing `api_gen.png` while a `/api/generate-cli`
request was held inside its subprocess, the CLI response came back as
`['api_gen.png', 'cli_new.png']` — the core path's file attributed to the CLI
request. `core.py:76` saves into `settings.output_dir`, which is exactly
`UPLOAD_FOLDER`, and `/api/generate` takes no lock. So the fix for IN-01 would
have to be correct *because of* that path, which it cannot currently be.

The non-silent variant (keep the set-diff, report the overwrite separately)
needs the same detection to decide there was one, so it does not escape the
problem. Returning the overwritten file is the other option and is only
SEC-08-safe once both write paths into the output directory are serialized as
one unit.

**This is Phase 3 work, not Phase 2.5 work.** `generate_image()` is named
Phase 3 scope by the assignment (duplicate request-object build) and is the
file that owns `/api/generate`; the correct fix is to serialize the two
endpoints' writes against one another (or give each request its own output
root), and that edit belongs where `generate_image()` is already being
rewritten. Until then, the silent-empty response is the SEC-08-safe behavior.

### IN-04: Unbounded argument surface after the subcommand — cost/quota abuse, not compromise

**File:** `src/imagai/web_server.py:249`
**Reason:** Note only per the orchestrator's assignment — no quota system
added, no gate added.

Recorded here for the tracker. The gate constrains the invocation prefix and
the subcommand, not the subcommand's arguments: `imagai generate -n 100`
spends API quota, `imagai list-engines --all` triggers an outbound fetch to
every configured engine. The endpoint is unauthenticated, so this is free
compute for any caller who can reach the port — but the loopback bind (D-06)
and the removal of the cross-origin grant (D-03) bound who that is, and
nothing beyond cost is reachable: `-o` is contained at the save layer
(`utils.py:182,223`), and `list-engines` masks API keys.

Worth noting as a side effect of the WR-02 fix rather than an open hole: the
endpoint now processes exactly one generation at a time, which caps
concurrent-quota amplification at one in-flight command. That does not bound
how *long* a caller keeps queueing work; a quota system remains the real
answer and is out of scope.

## Observations for later phases (not fixed — out of scope)

1. **A residual cross-request window survives WR-02, and it is not the one
   the review demonstrated.** `/api/generate` (`web_server.py:80-226`) writes
   into `settings.output_dir` — which *is* `UPLOAD_FOLDER`, by Phase 2's D-05
   — and holds no lock, so its writes land in a concurrent
   `/api/generate-cli` response. Reproduced with a mocked
   `generate_image_core` writing `api_gen.png` while a CLI request was in
   flight: the CLI response was `['api_gen.png', 'cli_new.png']`. So the fix
   chain closed the race the review showed (two generate-cli requests) and
   surfaced the one it did not (generate vs generate-cli). Closing it means
   serializing both write paths into the output directory as one unit — or
   giving each request its own output root — and both are edits to
   `generate_image()`, which Phase 3 already owns. Please treat this as a
   Phase 3 requirement, not a 2.5 leftover: SEC-08 is not fully satisfied
   until it lands.
2. **IN-01 is blocked behind the same thing.** Any honest fix for the silent
   overwrite needs overwrite detection, and overwrite detection is only safe
   once observation 1 is closed. Do not implement IN-01 first.
3. **The WR-02 lock is a global, not per-endpoint.** It is named
   `_GENERATE_CLI_LOCK` and taken only in `generate_image_cli()`. It is not
   reentrant and is never nested, so that is safe today — but if `/api/generate`
   is ever made to acquire it in Phase 3, keep the acquisition on the same
   order (never CLI-inside-generate) or the pair deadlocks.
